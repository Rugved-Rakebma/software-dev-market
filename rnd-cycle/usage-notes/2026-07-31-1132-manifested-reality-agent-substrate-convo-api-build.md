# rnd-cycle usage notes — manifested-reality-agent (substrate de-noct + conversation API build)

**Date:** 2026-07-31 · **Project:** `~/code/manifested/manifested-reality-agent` (single-user FastAPI + pydantic-ai backend, YAML vault, no DB) · **Session scope:** shipped phase-05 (substrate rename + entity-shape corrections) and phase-06 (the app-facing conversation API + 3 typed interview agents), across ~9 build commits, all direct-on-`main`.

This note is **feedback on the rnd-cycle skills**, written for whoever maintains them — where the flow fit, where it needed manual override, and the traps worth designing out. It's honest, not a complaint; the plan→build cadence carried a large, load-bearing change cleanly.

| Command | Used | Notes |

## The meta-theme: authoritative design lives in `docs/`, not `.rnd/`

Everything downstream traces back to one structural fact about this project:

- **`.rnd/spec/spec.md` does not exist** (only an `archive/` subdir — the v0.1 spec was archived long ago).
- **`.rnd/architecture/current.md` exists but is stale** — it's the *pre-impl Noct-MVP arch* that drove a prior phase and is now shipped/superseded.
- **The real design is hand-authored prose in `docs/design/*.md`** (`target-entities.md`, `conversation-api.md`, `convo-agents.md`, `reads-and-memory.md`) — richer than a REQ-ID spec, and the actual source of truth. As-built truth is in `docs/arch/*.md` (generated by an earlier `/rnd:arch-docs`).

Every rnd build-loop skill **hard-assumes `.rnd/spec/spec.md` + `.rnd/architecture/current.md` as its inputs** (prerequisites bail with "run `/rnd:spec` first" / "run `/rnd:design` first"; the context-loading + coder-bundling read those two files). On this project those two files are absent/stale, so **every `/rnd:plan` and `/rnd:c-build` invocation required manually overriding the sources**: point `rnd-planner` and `rnd-coder` at `docs/design/` + `docs/arch/`, and explicitly tell them to *ignore* `.rnd/spec/spec.md` (absent) and `.rnd/architecture/current.md` (stale). Plans' `requirements:` frontmatter cited **design-doc section anchors** (e.g. `conversation-api.md#2.1`, `target-entities.md#B4`) instead of `REQ-` IDs.

**Suggestion:** let a project declare alternate spec/arch sources (e.g. an `.rnd/config` pointer to `docs/design/` + `docs/arch/`), or make the skills degrade gracefully when `spec.md` is absent — treat design-doc anchors as first-class acceptance sources instead of erroring out. A lot of prose-design, solo-dev projects will never produce a formal `.rnd/spec/spec.md`, and that's fine.

### Why we "skipped `/rnd:spec`"
We didn't skip the *spec activity* — the design was worked out in depth over a long spec-before-code effort. We skipped the *formal `.rnd/spec/spec.md` REQ-ID artifact* because it would be **redundant re-derivation** of design docs that are already more detailed. For a solo dev with hand-authored design docs, the REQ-ID spec layer is over-formalization; the docs *are* the spec, in a better form.

## Why we're skipping `/rnd:c-verify`

`/rnd:c-verify` spawns three agents: `rnd-code-spec-checker` (vs `spec.md` REQ-IDs), `rnd-code-reviewer` (quality + integration), `rnd-code-analyst` (audit + security). On this repo:

1. **The spec-checker leg is degenerate** — there's no `spec.md` to check against.
2. **The other two default to `docs/arch/` as "as-built truth" — but our arch docs are stale.** They still describe the pre-phase-05 `Baseline`/`noct_*` world; phase-05/06 haven't been re-`arch-doc`'d yet. A vanilla verify would emit a **flood of false "drift" findings** against docs that are themselves out of date — noise, not signal.

So the honest, non-over-engineered "verify" for this repo is **one adversarial code-review subagent** reading the diff for (a) correctness + integration wiring and (b) conformance to the **design docs** — explicitly told to ignore the stale arch. That's a single opus reviewer, not a 3-agent report+backlog pipeline. Additionally, a lot of verify-value was already captured **inline**: the orchestrator independently verified each plan at build time (scoped staging, full-suite green, contract-present greps, entity-constraint spot-checks).

**Suggestion:** `/rnd:c-verify` should detect a missing `spec.md` and *skip* the spec-checker leg rather than run it empty; and it should not assume `docs/arch/` is fresh — let the caller name the conformance source (design docs here), or flag arch-staleness rather than treating arch as ground truth.

## `/rnd:c-build` friction

### 1. Worktree isolation is silently bypassed (twice-confirmed, re-confirmed this session)
`/rnd:c-build` spawns coders with `isolation: worktree` and has a circuit-breaker that **halts** if `git worktree list` doesn't grow one-per-plan-per-wave. In this harness, **isolation is silently bypassed**: the harness creates a worktree *directory* but the agent actually runs in the shared `main` cwd. Re-confirmed this session — a probe `isolation:worktree` spawn created a worktree dir, yet coders edited files in `main`.

Consequences / how we adapted:
- Ran **direct-on-`main`, no worktree** (user directive), which sidesteps the circuit-breaker entirely.
- For a **parallel wave** (phase-06 wave 2 = 3 plans), we ran the plans **sequentially, not in parallel** — without real isolation, concurrent coders would collide in the one working tree (index races, interleaved commits). This defeats c-build's core parallelism, but it's the safe choice here.
- **Stale-worktree spawns:** coders were sometimes spawned *into* a leftover worktree pinned to an old commit (missing `substrate/` + the design docs). Competent coders detected this and did all work in the main checkout via `git -C <main-path>`. We started adding a **"WORKTREE NOTE"** to every coder brief telling them to fall back to the main checkout if their cwd looks stale. Leftover worktrees mostly auto-cleaned (unchanged → removed), but a couple lingered and needed manual `git worktree remove`.

**Suggestion:** make the isolation circuit-breaker's failure mode a *first-class supported path* — i.e., an explicit `--no-worktree / sequential` mode for c-build (serialize plans within a wave, commit between) rather than a halt-and-diagnose. On harnesses where `isolation:worktree` is a no-op, sequential-on-main is the only correct way to run multi-plan waves, and the skill should support it natively instead of treating it as an error.

### 2. Built-in per-task commits vs a hard "ask before commit" rule
`rnd-coder` "commits per task" by design. This project's owner has a **hard rule: never commit without explicit in-the-moment approval; approval never carries forward.** The coders correctly recognized that *a spawn-prompt instruction is not the user's consent* and **deferred every commit to the orchestrator**, which verified then committed under the user's standing build authorization. Good behavior, but it means c-build's built-in commit step is effectively disabled here; the orchestrator owns commits.

Also: staging needed to be **strictly scoped** (`git add -A src/agent_mani/chat tests` only) because an unrelated **uncommitted docs/design + `.rnd` tracking batch** had to stay out of the code commits. c-build has no native notion of "commit only my plan's files, leave an unrelated working-tree batch untouched."

### 3. Interdependent tasks break "green per task commit"
c-build assumes each task ends green → one commit per task. That held for the **mechanical** plan (1a: pure rename, 3 green per-task commits). It **did not hold** for the semantic plans: the base-output redesign / entity split **breaks the existing tests until a later task rewrites them**, so tasks 1–3 are red-by-design and only the final task is green. For those, the correct shape is **one atomic green commit per plan**, not per task. The skill should acknowledge that some plans are internally interdependent and can only commit atomically.

### 4. No mid-plan crash recovery
One coder (phase-05 1b) hit an **API error mid-task**. Because isolation was bypassed, its ~99%-complete work sat **uncommitted in the main tree** (recoverable), and the orchestrator finished the last two gaps (a stale test + a missing retry test) by hand. c-build's resume is **per-wave via `progress.md`**, not mid-plan — there's no built-in "a coder died with uncommitted work in the tree, reconcile it." Worth a documented recovery path.

## `.rnd/` organization + the `progress.md` trap

- **Phase-dir naming:** prior phases were bare `phase-01`…`phase-04`. We adopted **descriptive suffixes** for the new ones — `phase-05-substrate-rename/`, `phase-06-conversation-api/`. Reads much better at a glance; recommend making descriptive phase-dir slugs the convention.
- **No `.rnd` files were renamed**, but `progress.md` bit us hard and it's worth calling out:

### The `progress.md` cumulative-file trap (a real usability landmine)
`.rnd/build/progress.md` is **cumulative across all phases**, and the statusline (`rnd-statusline.sh`) computes `pending = (count of plans/*/*.md files) − (## Completed bullets) − (## Deferred bullets)`. It reads *every* `*/*.md` under `plans/` (all phases, including `00-OVERVIEW.md`), so **`## Completed` must list one bullet for every plan file ever completed, across every phase.**

I mistook it for a phase-scoped rolling file and **overwrote it with a phase-05-only version** (2 Completed bullets). The statusline immediately read **"20 plans (17 pending)"** — because 20 files − 2 completed − 1 deferred = 17. Fix was to `git checkout` the prior cumulative file and **append** the new phase's bullets. (A prior phase's own `progress.md` even documents an *earlier* instance of a similar statusline-count break — someone moved shipped plans into a `closed/` subdir, which hid them from the `plans/*/*.md` glob.)

**This is easy to get wrong twice.** The skill doc says "maintain a single rolling progress file" and "one bullet per plan (not per wave) so the statusline can compute pending count" — but it never states loudly: **"this file is CUMULATIVE across ALL phases; never scope-overwrite it; append per plan; the statusline counts files-on-disk minus your Completed/Deferred bullets."**

**Suggestions:**
- Put a one-line header banner in the `progress.md` template: *"CUMULATIVE across all phases — append, never overwrite. Each `## Completed`/`## Deferred` bullet = one file under `plans/*/*.md`; the statusline counts files − these bullets."* (We added exactly such a banner to this project's file.)
- Consider deriving completion from a per-plan status field in the plan's own frontmatter (or a tiny sidecar), so the statusline count can't drift from a hand-maintained bullet list.
- The `(none)` placeholder under `## Deferred` is dangerous: a literal `- (none)` bullet is *counted* as a deferred plan. Use non-bullet placeholder text.

## What worked well (so it isn't all friction)

- **Plan quality.** `rnd-planner`, once pointed at the right docs, produced genuinely good plans: `file:line` anchors, concrete `Done:` gates (grep/`python -c`/pytest), explicit IN/DEFERRED boundary sections, and risk notes that named the real hazards (deep-merge clobbering, per-phase-write idempotency, base-redesign blast radius).
- **Coder quality.** `rnd-coder` produced typed pydantic models, closed enums, real tests (stubbed LLM per the repo's patterns), and preserved subtle invariants (retry-safe idempotent writes, provenance server-stamping) across a schema split — with honest "beyond-brief" disclosure.
- **The plan → build → verify-inline → commit cadence** was a strong rhythm for a large change: 4 plans / 2 waves / 4 atomic commits for phase-06, full suite 325 → 353, boundary held (zero streaming/reads leaked into a "non-streaming, shaped-for-later" phase).
- **`progress.md` + statusline** (once handled correctly) gave good at-a-glance state across a multi-phase build.

---

## One-line takeaways for the maintainers

1. **Don't hard-require `.rnd/spec/spec.md` + `.rnd/architecture/current.md`** — many real projects keep design/arch as prose in `docs/`. Let the caller name the sources; degrade gracefully; accept doc-anchors in place of REQ-IDs.
2. **`/rnd:c-verify` should skip the spec-checker when there's no spec, and not assume `docs/arch/` is fresh.** For a no-spec repo, "verify" collapses to a single design-doc-anchored code review.
3. **Support a native `--no-worktree / sequential` c-build mode** for harnesses where `isolation:worktree` is silently a no-op; make sequential-on-main first-class, not a circuit-breaker halt.
4. **Acknowledge interdependent plans** that can only commit atomically (not green-per-task), and a mid-plan crash-recovery path.
5. **Make `progress.md`'s cumulative nature un-missable** (template banner) — the statusline silently misreports when it's scope-overwritten, and it's a repeat offender.
